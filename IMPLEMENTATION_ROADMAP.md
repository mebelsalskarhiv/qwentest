# План реализации Virtuoso MES по результатам аудита

**Дата:** 7 сентября 2026 г.
**Базовый подход:** modular monolith с чёткими доменными границами, постепенное выделение сервисов только при подтверждённой необходимости.
**Цель:** перейти от MVP к полнофункциональной MES-системе без расширения функциональности поверх небезопасной мультитенантной базы.

## Принципы реализации

- Сначала безопасность, изоляция данных и тестируемость.
- Каждая новая сущность сразу получает `tenant_id`, миграцию, API, UI и тесты.
- API не доверяет `tenant_id` из тела запроса: tenant берётся из текущего пользователя/контекста.
- Доменные статусы задаются явными переходами, а не произвольным редактированием строки.
- Интеграции строятся через outbox/inbox и идемпотентные операции.
- Сначала эмуляторы и контрактные тесты, затем подключение реального оборудования.

## Фаза 0. Безопасность и стабилизация

**Срок:** 1-2 недели.
**Приоритет:** критический.

### Задачи

1. Добавить `tenant_id` во все tenant-модели:
   - материалы и категории;
   - поставщики;
   - продукты и BOM;
   - производственные заказы и операции;
   - рабочие центры;
   - сотрудники, подразделения и клиенты;
   - станции и складские движения.
2. Выпустить Alembic-миграции с заполнением существующих demo-записей.
3. Добавить единый tenant-aware repository/query helper.
4. Закрыть все API фильтром по текущему tenant.
5. Реализовать `require_permission` и применить его к CRUD.
6. Запретить изменение и удаление чужих объектов.
7. Зашифровать пароли станций.
8. Привести demo seed к одному источнику и убрать дублирующиеся сценарии пользователей.
9. Добавить тесты tenant isolation и RBAC.

### Критерии готовности

- Пользователь tenant A не видит данные tenant B.
- Пользователь без permission получает 403.
- Superadmin API недоступен обычному tenant admin.
- Повторный seed не создаёт дубликаты.
- Все критичные endpoint имеют тесты 200/403/404.

## Фаза 1. Производственный домен

**Срок:** 3-5 недель.
**Приоритет:** высокий.

### Задачи

1. Создать сущности:
   - `StageType`;
   - `ProductionStage`;
   - `WorkOrder`;
   - `WorkOrderFile`;
   - `WorkOrderComment`;
   - `WorkOrderTimeline`.
2. Реализовать статусные переходы и проверки зависимостей.
3. Добавить назначение исполнителя, станции и участка.
4. Связать материал, заказ, этап, наряд и результат производства.
5. Перевести Kanban с заказов на WorkOrder.
6. Добавить QR-коды для нарядов и материалов.
7. Реализовать расширенные фильтры Kanban.
8. Добавить аудит всех переходов статусов.

### Критерии готовности

- Заказ проходит цепочку этапов от планирования до завершения.
- Наряд нельзя начать без готового предыдущего этапа.
- Каждая операция имеет исполнителя, станцию и историю.
- QR открывает карточку нужного объекта.
- Kanban показывает реальные WorkOrder.

- Нет межtenant-утечек в автоматических тестах.
- У каждой бизнес-операции есть permission.
- WorkOrder проходит полный статусный workflow.

- Demo tenant наполнен данными нового домена.
